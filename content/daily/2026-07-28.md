## 今日概览

「开源追平闭源」的说法每隔几个月都会出现一次。这一次的基准数据确实很接近，但把评测拆细之后，差距集中在三个地方。

```stat
综合基准差距 | 3.1 pts | -2.4
长上下文差距 | 12.6 pts | +0.8
工具调用差距 | 17.2 pts | +1.5
```

---

## 差距一：长上下文的稳定性

在 128K 以上的输入长度下，开源权重的「中段遗忘」现象更明显。典型表现是能准确复述开头与结尾，但对中间 40% 的内容召回率显著下降。

| 输入长度 | 开源召回率 | 闭源召回率 |
| --- | --- | --- |
| 32K | 94% | 96% |
| 128K | 71% | 88% |
| 512K | 43% | 74% |

> [!NOTE] 实践提示
> 如果你必须用开源权重处理超长文档，把「检索 + 分段」保留下来会比直接投喂更稳。

## 差距二：工具调用的参数构造

这是差距最大的一项。失败模式并不是不会调用工具，而是参数细节出错：

- 日期格式不符合 schema
- 可选参数被误填为 `null` 而不是省略
- 多轮调用后忘记携带上一步返回的 ID

```json
{
  "tool": "search_orders",
  "args": { "since": "上周一", "status": null }
}
```

上面这种输出在严格 schema 校验下会直接失败，而模型往往不会自我修正。

> [!TIP] 缓解方式
> 在工具层做一层「宽松解析 + 归一化」，把自然语言日期、空值、别名统一处理掉，
> 实测可以把工具调用失败率降低一半以上。

## 差距三：安全对齐的一致性

开源权重的对齐强度差异很大，且微调后极易退化。生产环境使用时，输入输出两侧的独立审核仍然是必要的。

```quote
开源模型的能力是可复现的，对齐是不可复现的。
— 一位模型评测研究者
```
